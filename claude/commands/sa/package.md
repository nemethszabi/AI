> Version: 3.0.0 — major: rendering moved out of this file into `sa-framework/builders/`, per the new
> `sa-framework/RENDERING-CONTRACT.md`. This command now checks the gates, runs the builder and relays
> its report; it no longer describes document structure, and it must not. 2.1.0 — the workbook followed
> `ESTIMATION-METHOD.md` v1.5 §11.5. 2.0.0 — the gate began requiring two verdicts.

<objective>
`/sa:package <slug> [type] [--pdf]` renders `ai/sa/<slug>/`'s JSON artifacts into the files a client
receives, under `ai/sa/<slug>/deliverables/`.

**This command does not decide what a deliverable looks like.** Section order, workbook tabs, tables,
figures, numbering and rounding are fixed by `sa-framework/RENDERING-CONTRACT.md` and implemented in
`sa-framework/builders/`. Your job here is the four things a script cannot do: resolve the slug, enforce
the gate, run the builder, and relay what it reports.

That boundary is the point of this version. When this file described the document instead, the model
rewrote the build logic on every run — and one shipped engagement acquired a cover page saying version
9.0 above an information table saying 1.0, an internal "do not edit this file by hand" note in the client's
copy, and a workbook missing the tab the specification called for. The specification was right each time.
Regenerating an implementation of it forty times was the defect.

This is still the only command in the namespace that produces something a client sees, so it is still the
only one with a hard gate — one refusal point reading two verdicts:

| Verdict | From | Checks |
|---|---|---|
| `sa-audit` | `/sa:audit` | do the JSON artifacts agree with each other, by ID? |
| `sa-slop` | `/sa:slop-check` | is the prose a human will read grounded and free of machine-tells? |

Neither substitutes for the other: an offer whose every ID resolves can still quote an invented benchmark,
and an offer with clean prose can still be missing a `must` requirement.
</objective>

<process>
<step name="resolve-args">
Resolve the slug as `/sa:design` does — an argument naming an existing engagement folder wins, otherwise
glob for `engagement.json`; exactly one match uses it, several ask which, none stops and names `/sa:triage`.

Parse `$ARGUMENTS`:

- **`type`** — `offer` (default), `estimation-pack`, `hld`, `lld`, `pitch`, or `all`. For `all`, build what
  the lane in `engagement.json` calls for (`ARTIFACT-SCHEMAS.md §4.1`): `rom` → offer; `offer-sow` →
  offer + estimation-pack; `full-design` → those plus hld, lld and pitch.
- **`--pdf`** — also export PDF. Worth defaulting on for anything going to a client: the builder drives
  Word to compute the table-of-contents field, so the DOCX is saved with its contents page already filled
  in rather than depending on the reader accepting a prompt.
- **`--version=NN`** — force a version number. Omit it and the builder takes the next one.
</step>

<step name="gate-check">
Compute `inputs_hash` fresh, per `ARTIFACT-SCHEMAS.md §5`: `git hash-object` over whichever of
`requirements.json`, `architecture.json`, `estimation.json`, `risk-register.json`, `offer.json` exist,
first 12 characters each, joined in that fixed order. Outside a git repo, fall back to `sha256sum`.
Content-based — **never** mtimes. Exclude rendered `.md`, `deliverables/`, `diagrams/` and snapshots.

Read the newest `audit/audit-*.md` **and** the newest `audit/slop-*.md`, and take the fenced
```` ```sa-verdict ```` block from each. **Match them by their `gate:` field** — `sa-audit` and `sa-slop` —
never by filename or by prose. A block with a missing or unrecognized `gate:` counts as a missing gate.

All four conditions must hold: each verdict is `PASS` or `PASS-WITH-WAIVERS`, and each recorded
`inputs_hash` matches the one just computed. Both gates hash the same input set, so one computation serves
both comparisons.

If any fails, print and **abort**:

```
Cannot package — gate failed or stale:
  Audit (sa-audit): <verdict or "not run"> @ <timestamp>
                    <hash match | STALE — artifacts changed since the audit>
  Slop  (sa-slop):  <verdict or "not run"> @ <timestamp>  [ran on: <model>]
                    <hash match | STALE — artifacts changed since the scan>

Run <the failing command(s)>, then retry.
```

Name only the gates that actually failed — telling someone to re-run a gate that passed teaches them to
skim the message. When `sa-slop` passed but ran on the same model that wrote the artifacts, add one
advisory line, not a refusal: `slop scan ran on <model>, same family as the author — consider
/sa:slop-check <slug> --model=<other> before this goes out` (`ARTIFACT-SCHEMAS.md §9`).
</step>

<step name="run-builder">
Run the builder. Resolve `<config-root>` by `ARTIFACT-SCHEMAS.md §8`'s chain (`$CLAUDE_CONFIG_DIR`, then
`~/.claude`) — never assume `~/.claude`, since more than one redirected root exists on this machine:

```bash
python <config-root>/sa-framework/builders/build.py "ai/sa/<slug>" \
    --type <offer|estimation-pack|all> [--pdf] [--version=NN]
```

The builder resolves both profiles, validates the artifacts against their schemas, renders the figures,
fills the branded template, writes the files and prints a report. A whole engagement builds in a few
seconds.

**Read its output; do not re-derive its work.** In particular:

- Do **not** write a one-off Python script to build or patch a deliverable. If the builder cannot produce
  what is needed, that is a change to `builders/`, made deliberately and once — not a script in an
  engagement folder. Ad-hoc `_patch_*.py` files beside the artifacts are how one engagement acquired
  eleven of them and a `__pycache__` directory.
- Do **not** hand-edit a built DOCX or XLSX. The fix for a wrong figure is the artifact it came from.

**If the builder exits non-zero**, it found a defect, not an obstacle. Relay its error verbatim and name
the command that fixes it — almost always re-running the step that owns the artifact. A `rollup` using
key names that are not in the schema means `/sa:estimate` has not been re-run since the artifact was
hand-edited; the builder deliberately will not guess which invented key meant which standard one.
</step>

<step name="build-other-types" condition="type in (hld, lld, pitch)">
`offer` and `estimation-pack` are the builder's. `hld`, `lld` and `pitch` are not yet, so they still go
through the `office-doc-builder` skill's `lib/` helpers — import them, never write raw
openpyxl/python-docx/python-pptx styling inline.

- **`hld`** → DOCX from `architecture.json`. **`lld`** → DOCX from `detailed-design.json`.
- **`pitch`** → PPTX, 8–12 slides: Title · Their objectives · Our understanding · Solution · Delivery ·
  Investment · Risks & controls · Next steps.

Say in the relay that these took the older route, so the difference in consistency is known rather than
discovered. Moving them into `builders/` is tracked work, not a silent gap.
</step>

<step name="save-snapshot">
Write `deliverables/.snapshots/<type>-v<NN>.json` bundling the artifacts that drove this build, so a later
comparison has a baseline. Never delete an old snapshot — each pairs with its version.
</step>

<step name="update-state">
Update `STATE.md` in the canonical shape from `ARTIFACT-SCHEMAS.md §6`: phase `package`, last command
`/sa:package`, next `/sa:status`. Record what was built and at which version in the appended phase-history
line. Append; never rewrite prior lines.
</step>

<step name="relay">
Relay the builder's own report, not a paraphrase. It already names each file with its version and size,
the workbook's sheets, whether the PDF was produced and whether the fields were refreshed.

Add, every time, the two things a reader would otherwise assume went well:

- **which render profile and which document profile were used** — including the word "unbranded" and the
  reason, when no template resolved
- **which model each gate ran on**

Then repeat the builder's findings. They are reported, not fatal, and they are the most useful part of the
output: a must-requirement with no estimate line, a paragraph over the prose budget, a diagram edge
naming a component that does not exist. Never summarise them away to make a run look clean.

If `onepager/` is empty and this was an `offer` build, mention `/sa:onepager <slug> summary`.
</step>
</process>

<rules>
- **No build without a fresh PASS from BOTH gates.** Refusal is correct, and the remedy is re-running
  `/sa:audit` and/or `/sa:slop-check`, never relaxing the check (`CONSTITUTION.md` Article III).
- **Gates are matched by their `gate:` field**, never by filename.
- **Never describe document structure in this file.** It lives in `RENDERING-CONTRACT.md` and
  `builders/`. A command that restates it has created a second source of truth, and the two will drift.
- **Never write a one-off build or patch script.** Change the builder, once.
- **Never hand-edit a built deliverable.** Fix the artifact and rebuild.
- **Unbranded output is announced, never silent.**
- **Freshness is content-based.** Packaging's own outputs never re-stale the gate that permitted them.
- **Never overwrite a versioned deliverable** — the builder increments `v<NN>`.
- **Say what didn't work.** A missing Word installation, a skipped figure, an unfilled placeholder is
  reported plainly — never papered over.
- **Never commit.** Deliverables are the human's to review and commit.
- **A rate card never appears in a client-facing file** — only the arithmetic consequences someone chose
  to show (`ESTIMATION-METHOD.md §7`).
</rules>
