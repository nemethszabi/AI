# SA Framework — Rendering Contract

**Binding** and **tool-agnostic**. Governs how an engagement's JSON artifacts become the files a
client actually receives: what goes in them, in what order, and which decisions are a matter of
configuration rather than judgment.

Its three siblings govern different axes:

| File | Governs |
|---|---|
| `ARTIFACT-SCHEMAS.md` | **shape** — the JSON every artifact must conform to |
| `ESTIMATION-METHOD.md` | **method** — how numbers are derived and what they may be used for |
| `PIPELINE.md` | **sequence** — which step runs when, on what, with what obligations |
| **this file** | **rendering** — what the deliverable looks like, and who decides |

---

## 1. Why this file exists

Packaging used to be a prose specification that a model re-implemented on every run. The
specification was good. The output was not, and the gap between them is the reason this document
and the `builders/` package exist.

Three defects, all from one real engagement's shipped deliverables:

- The offer's cover page said **Version 9.0** while its Document Information table said **1.0**.
  Two places state the version; the generator updated one.
- The offer's body opened with *"Generated from offer.json revision 9. Do not edit this file by
  hand."* — an internal note, in a document sent to a client.
- The specification called for a five-tab workbook. The delivered workbook had four. The **Rollups**
  tab, which answers *how much of this is not build work*, was simply absent.

None of those is a reasoning failure, and no amount of prompt improvement fixes them reliably,
because the failure mode is variance, not misunderstanding. A job that must produce the same result
every time belongs in code that produces the same result every time.

So the division of labour is now explicit:

| Decision | Owner |
|---|---|
| What to say — scope, wording, what is disclosed, what is excluded | the `req-*` agents |
| How it is laid out — order, tables, figures, numbering, rounding | `sa-framework/builders/` |
| Which sections and tabs exist for **this client** | a **render profile** |
| Fonts, colours, logo, approved legal boilerplate | a **document profile** (`ARTIFACT-SCHEMAS.md §8`) |

A command that regenerates layout logic in-context has taken back a decision this contract assigns
to code, and is non-conforming even if its output happens to be right that time.

## 2. The two profile axes, and why they are separate

**Document profile** — `document-data/templates.yaml`. The brand shell: which DOCX template, which
placeholders map to which fields, which sections are approved boilerplate and which are typography
samples to delete. Selected by **language**.

**Render profile** — `document-data/render-profiles/*.yaml`. The content structure: which sections
in which order, which workbook tabs, and which commercial constraints apply. Selected by **client**.

They are separate because they vary independently. A Hungarian-language offer to a Romanian client
is a real combination, and one collapsed "profile" cannot express it. Separating them also keeps a
single large customer's document preferences out of the shared builders, where an
`if client == "Vodafone"` branch becomes everyone's default the first time somebody forgets to
guard it.

### Resolution order

Render profile, first hit wins:

1. `engagement.json.render_profile` — an explicit human decision, never overridden.
2. A profile whose `matches.client_patterns` matches the engagement's client name.
3. `standard`.

`/sa:package` **reports which profile was chosen and why**, every time. A structural choice the
reader has to infer from the output is a choice nobody reviews.

## 3. The standard deliverable shapes

### 3.1 The offer DOCX

An offer is read by people who will not read the workbook. It carries **one** effort figure, states
what is in and out, and shows the shape of the work. Detail belongs in the workbook.

| Section | Contains | Why |
|---|---|---|
| Cover and Document Information | From the template's placeholders | The version appears twice and is written by one function, because it has drifted |
| Approved boilerplate | Verbatim from the template | Legal and marketing text, never regenerated |
| **Contents** | A real Word TOC field | Styled `Title`, never a heading — see §5 |
| Executive summary | 2–3 paragraphs a decision-maker can act on alone | |
| Our understanding | Their objectives, in their vocabulary | Comprehension before proposal |
| Solution | Principle · **component diagram** · component table · data protection | The figure is the fastest way to convey an architecture |
| Scope | In scope · coverage · **named-and-not-in-the-figure** · optional · out of scope | |
| Delivery approach | Phase table with weeks · **timeline chart** | |
| Effort | **One figure** · phase breakdown that reconciles · optional · support | |
| Assumptions, dependencies and risks | Three tables, each with its consequence | |
| Questions to confirm before start | Only when open decisions exist | |
| Commercial terms | Validity, basis, change control | |

Three rules that are not negotiable:

- **One effort figure.** The committed PERT total, rounded to whole man-days. Best, likely and PERT
  live in the workbook (`ESTIMATION-METHOD.md §11.5`). `worst` appears nowhere.
- **The effort table adds up.** A phase breakdown summing to the baseline under a row labelled
  *total committed* is the "right number beside the wrong other number" defect §11.1 exists to
  prevent. Contingency gets its own visible row between the two.
- **"Out of scope" and "named, and not in the figure" are different sections.** The first says we
  are not doing it. The second says we discussed it, it is real, and it is not priced here.
  Collapsing them is how a client later believes something was included.

### 3.2 The estimation XLSX

Management first, detail after. Every line checkable one at a time.

| Sheet | Answers |
|---|---|
| **Summary** | What does this cost, and what is it made of? Waterfall, then breakdown by phase and by work type with the non-build share stated |
| **How to read** | What is a K-category? What is PERT? Why is `worst` not shown? |
| **Rollups** | The three sub-rollups of `ESTIMATION-METHOD.md §11.2` |
| **Line items** | Every line: best, likely, PERT, plus the AI-leverage justification |
| **Timeline** | Phases with weeks and deliverables |
| **Assumptions** | Assumptions and exclusions, each with its consequence |
| **Risks** | The register, plus what the contingency buys, risk by risk |
| **Not estimated** | Named, deliberately unpriced, with the reason |
| **Coverage** | Requirement × component × estimate line |

Rules:

- **Read stored totals; never recompute one.** Every headline comes from `estimation.json`'s
  `rollup`. Arithmetic *rows* carry live cell formulas so a reader can check the sum in the
  workbook — but the builder never substitutes its own arithmetic for a stored figure.
- **`worst` is written to no sheet and no hidden column** unless `basis.render_worst` is true. A
  hidden column is one unhide away from the anchoring the rule exists to prevent.
- **Baseline and optional rows are visually separated and never interleaved**, each subtotalling to
  its Summary row.
- **A summary line never sits inside a summed range.** It goes in a footer, or the next person to
  give it a value double-counts it.

### 3.3 Figures

Both figures are rendered deterministically from the artifacts, on a **white background**, by
`builders/diagram.py`:

- **Component view** — components in layers, arrows between them, vendor-built boxes visually
  distinct from what already exists. Ordered by a barycentre pass so edges do not cross needlessly.
- **Timeline** — a phase bar chart that shows overlap where the plan has overlap, because a plan
  whose build phases overlap is a different commitment from one that is strictly sequential.

Mermaid and `mmdc` remain correct for the varied, exploratory diagrams an HLD carries. They are the
wrong tool for the one figure that must appear in every offer: `mmdc` is a Node toolchain that is
frequently absent, its theme decides the background, and its auto-layout drifts between versions so
the same architecture renders differently in v6 and v7 and a reader assumes the design changed.

## 4. Client-specific rendering

A client whose sales side asks for a specific document shape gets a render profile, not a code
branch. The profile `extends: standard` and overrides only what genuinely differs.

Section lists merge structurally rather than being restated: an override matching an inherited `id`
replaces that section in place; a new `id` is inserted where its `position` says (`first`, `last`,
`before:<id>`, `after:<id>`). A client profile therefore adds one section without copying the eight
it inherits — and a copied list is exactly what stops tracking the base.

The loader **reports any override whose value already equals the inherited one**. Harmless today,
and precisely what stops tracking the base tomorrow.

What belongs in a client render profile:

- section order, and sections that exist only for this client
- workbook tabs that exist only for this client
- commercial constraints (`effort_only`, `forbid_currency`) stricter than the framework default
- the document subtitle, when the account expects a consistent one

What does **not**:

- anything about fonts, colours or logos — that is the document profile
- content. A profile says a cluster-coverage table exists; the data for it comes from the
  artifacts, and when the artifacts carry none the section renders without it **and says so**.
  A profile never causes a table to be invented.

## 5. Word mechanics that have caused real defects

Recorded here because each was found the expensive way, and each looks like it is already handled.

- **A placeholder split across runs.** Word's editing history stores `[Customer Name]` as
  `[Customer ` + `Name]` often enough that naive per-run replacement misses it, and the client's own
  name ships unreplaced. Match on the joined paragraph text.
- **The version appears twice.** Cover paragraph and Document Information cell. One function writes
  both.
- **A "Contents" heading lists itself.** Word builds a TOC from outline levels, so a Heading 1
  "Contents" becomes entry 1 and pushes every section number up by one. Overriding the paragraph's
  outline level looks like the fix and is not — Word normalises the override away when it re-saves
  during PDF export. Use `Title`, which Word never collects. Do not use `TOC Heading`: it is
  commonly based on Heading 1 and shares its numbering list.
- **The TOC field is inert until Word computes it.** python-docx inserts a genuine field; the
  entries and page numbers depend on final pagination. Where Word is installed, `builders/pdf.py`
  drives it to refresh the field, save the populated DOCX and export the PDF. Where it is not, the
  builder **says the field is unpopulated** rather than implying otherwise.
- **Two update passes, not one.** The first inserts the entries; inserting them shifts the
  pagination the page numbers were computed against. One pass leaves a TOC off by a page.
- **A legacy console code page.** A single em dash in a build report raised `UnicodeEncodeError`
  *after* the files were written — a successful build reported as a crash. Reconfigure stdout.

## 6. Conformance

An implementation conforms when:

1. Deliverables are produced by `builders/`, not by layout logic regenerated in-context.
2. Artifacts are validated against their schema **before** any document is written, and a
   non-conforming artifact names the command that fixes it.
3. The render profile and the document profile are both **reported** on every build, including the
   words "unbranded" when no template resolved.
4. No client-facing string carries internal provenance. The builder refuses the build on a hit
   rather than stripping it, because a leak means an artifact is wrong.
5. Effort rounding follows `ESTIMATION-METHOD.md §1`: whole units for any rollup or total, one
   decimal per line, rounded on output and never in the stored value.
6. A versioned deliverable is never overwritten.
